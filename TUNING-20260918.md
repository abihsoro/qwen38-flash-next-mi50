## Measured performance

These are single-request results at **150 W per GPU**, with 128 generated tokens. Each prompt family has two complete warmups and three scored requests. The table reports the median of the three family medians: prose, code and reasoning. Prompt lengths are exact token counts, with zero prefix-cache hits on every scored request.

| Prompt tokens | Reference TTFT | Improved TTFT | Reference effective PP | Improved effective PP | PP increase | Improved decode |
|---:|---:|---:|---:|---:|---:|---:|
| 128 | 0.654 s | 0.374 s | 195.8 tok/s | 342.7 tok/s | 75% | 56.4 tok/s |
| 512 | 1.129 s | 0.778 s | 453.6 tok/s | 657.7 tok/s | 45% | 56.2 tok/s |
| 1,024 | 1.649 s | 1.331 s | 620.8 tok/s | 769.1 tok/s | 24% | 55.9 tok/s |
| 1,536 | 2.719 s | 1.805 s | 565.0 tok/s | 851.1 tok/s | 51% | 56.1 tok/s |

The 128/512 rows come from `combined1024`; the 1,024/1,536 rows come from `chunk2048`, the selected configuration. Both combined configurations use the same MoE tiles, router, power cap and CPU placement. The smaller prompts fit into one prefill chunk under either budget; the table does not pretend they were separately benchmarked under both budgets. Reference results are from the fully warmed repeat control.

**Effective PP is prompt tokens divided by server time to first token**, including first-token work. It is not a GPU-only GEMM rate. Decode excludes prompt processing and subtracts every token in the first streamed burst before dividing by the server's first-to-last-token interval. This also handles speculative bursts correctly. Raw client timing, server metrics, returned token IDs, cache counts, hashes, speculative metrics and hardware snapshots are retained.

The historical approximately 47.7 tok/s gate timed the whole HTTP request. It is not directly comparable to these decode rates. The corrected reference is approximately 55–56 decode tok/s on this corpus. The selected router provides a modest serving improvement; this campaign did **not** produce a 10% general decode improvement.

## What was selected

- **Prefill MoE tiles.** The real EP workload has 512 global experts, 128 local experts, top-10 routing and an explicit global-to-local expert map. The old tuner bypassed its candidate settings for small batches and allowed its largest small-batch entry to control much larger prefills. The replacement search targets actual prefill batches and preserves small-batch defaults. All 68 initial cases and 65 extended cases passed their numerical comparisons. The MoE-only full-model arm matched all nine control prompt cases exactly, across all 27 scored outputs.
- **Mask-aware top-10 router.** The guarded gfx906 path supports FP16 logits, 512 experts, top-10 softmax routing, renormalization and batches of 1–8. It preserves padding indices, tie handling, invalid-logit handling and dynamic masks under graph replay. The final numerical suite passed 160 input/mask cases plus replay checks. Production logs and the trace confirm that the new path actually runs. The first prototype declined padding and fell back to the original; that arm is explicitly marked as a fallback, not an optimization result.
- **2,048-token chunk budget.** At a 1,536-token prompt, the combined stack improved from 2.114 s TTFT with 1,024-token chunks to 1.805 s with 2,048-token chunks. A 512-token budget was worse: 2.338 s. The model-length limit remains 2,048, with at most four active sequences.

The selected MoE file uses M/N/K tiles of 8/64/32 at batch sizes 128, 256 and 512; 32/64/32 at 1,024; and 32/64/32 with one stage at 1,536 and 2,048. Earlier entries retain two stages. The configuration is isolated in its own tuning folder. No compiled extension was rebuilt; every original binary hash still matches.

For the collective sweep, automatic-policy worst-rank medians were approximately 19.0, 15.6, 15.9 and 18.4 µs at 5, 10, 15 and 20 KiB. A one-block cap took 40.4, 73.5, 108.5 and 139.9 µs. These measurements do not support reducing the block cap for this topology.

The clean reference trace contains 97 collectives and 48 routing calls per decode step. Fourteen complete aligned steps show median collective start skew of 12.4 µs and completion skew of 1.2 µs. Collective duration includes waiting for other ranks; it is not all removable transport cost. Profiling perturbs execution, so unprofiled serving results decide adoption. The selected router is visible in the second trace, but differing trace windows make a precise subtraction of total profiled wall time inappropriate.

## Correctness and limitations

The combined 1,024-chunk arm matched 8 of 12 reference token sequences; the 2,048-chunk arm matched 4 of its 6 reference cases. Changes in floating-point reduction and chunking can change greedy continuation when logits are close. The source and numerical tests support the new computation, but it is **not bitwise equivalent** to every reference output.

The original reference and all completed combined/chunk arms passed the same **11 of 12** small answer checks. The packing question failed in the reference too: it began with “4” despite deriving the correct lower bound of 7 later. The initial permissive grader counted the later mention; it was corrected to grade the first requested answer. Both original and corrected grading artifacts are preserved. This small corpus is a regression smoke check, not a general model-quality evaluation or an independent full-model golden.

INT8 weight-quantization error is separate from implementation error. Numerical agreement with dequantized weights does not certify language-model quality. INT8 was not adopted. No result here establishes multi-request aggregate throughput, long-context performance beyond the configured limit, or a 75 tok/s target.

## Final operating state and rollback

The selected service passed its post-restart health check and answered the arithmetic smoke request correctly. Its recorded [historical MTP0 state](campaign/final-state-mtp0.json) identifies PID <pid> and launch `<launch-tag>`. It is `qwen38-flash-next` on port **8002**, using TP4+EP, FP16 dense weights, the existing AWQ experts and INT4 PLE sidecar, full decode graphs and compilation disabled. GPU power caps are 150 W; DPM policy is `auto`. MTP, TunableOp and dense INT8 are off. The original generic INT8 gate has been restored.

A temporary host ZFS ARC maximum of 128 GiB did not establish a serving-throughput benefit or eliminate the sidecar scan. The original **16 GiB maximum and zero minimum parameter** have been restored; persistent host settings were never changed. The optional higher-power and clock-policy experiments were not run. Initial benchmarks overlapped background sidecar prefaulting; final controls and comparisons wait for the 32 GB prefault operation to finish. `/health` alone is not that readiness gate.

From the directory containing this report, on the client with the existing root SSH access:

```bash
bash campaign/scripts/launch.sh balanced
bash campaign/scripts/launch.sh reference
bash campaign/scripts/launch.sh stop
```

The launcher reapplies the 150 W contract on Proxmox, then starts the selected LXC preset. `reference` disables the new router and MoE configuration and restores the 1,024-token chunk budget. It replaces only a server tracked by the campaign controller, verifies process identity, and refuses an unrelated listener on port 8002. There is no new boot service or automatic restart policy.
